# Payments ledger — install & operating notes

Every shilling received is a row in `public.payments` with a receipt number. `invoices.paid_kes`,
`balance_kes` and `status` are maintained **by the database** from that ledger.

Methods: cash (with change), M-Pesa STK push (Daraja / Paystack / Flutterwave), M-Pesa code from
till/paybill, card checkout (Paystack / Flutterwave / Pesapal), POS card, bank transfer / RTGS / PesaLink,
cheque, Airtel Money, and any mix of them in one split.

## Install (what was done on the live project, 2026-11-14/15)

| Step | File / command | Notes |
|---|---|---|
| Check | `docs/sql/01_check_current_supabase.sql` | read-only, one table back |
| Payments DB | `docs/sql/02_install_payments.sql` | moves an empty old `payments` table aside, fixes `sync_invoice_totals` |
| Security fix | `docs/sql/03_security_hardening.sql` | stops self-promotion to admin / joining other hospitals; lists all admins |
| Functions + secrets | `powershell -ExecutionPolicy Bypass -File scripts\deploy-payments.ps1` | asks you to log in; puts the sweep SQL on the clipboard |
| Sweep | paste the clipboard into SQL Editor | enables pg_cron + pg_net and schedules every 3 min |

The `.sql` files are generated by `node docs/sql/build-install.mjs` from the migrations. Always run them
with **"Run without RLS"** in the Supabase SQL editor.

### Manual equivalent

1. **Back up the database.** The migration copies historic `paid_kes` into the ledger (`LEG-…` receipts).
2. Apply `supabase/migrations/20261114000000_payments_ledger.sql` (`supabase db push` or the SQL editor).
   It is safe to re-run.
3. Merge `supabase/config.toml.snippet` into `supabase/config.toml`, then:
   ```bash
   supabase secrets set PAYMENTS_WEBHOOK_SECRET=$(openssl rand -hex 32) \
                        PAYMENTS_CRON_SECRET=$(openssl rand -hex 24) \
                        SITE_URL=https://your-hms-domain.co.ke
   supabase functions deploy payments-initiate payments-status payments-refund payments-webhook --no-verify-jwt
   ```
4. In the app: **Settings → Payments**. Enable methods, choose providers, enter credentials (**sandbox first**).
5. Register each provider's webhook URL (shown on that screen). Flutterwave also needs its secret hash saved there.
6. Schedule the sweep that catches lost webhooks:
   ```sql
   select cron.schedule('payments-sweep', '*/3 * * * *', $$
     select net.http_post(url := 'https://<project-ref>.supabase.co/functions/v1/payments-status',
       headers := jsonb_build_object('Content-Type','application/json','x-cron-secret','<PAYMENTS_CRON_SECRET>'),
       body := '{"sweep":true}'::jsonb) $$);
   ```

## Who can do what (enforced in the database, mirrored in `src/access.js`)

The role is taken from, in order: `hospitals.owner_email` (always admin) → the user's `staff.role`
(matched by email) → `hospital_users.role`. Job titles are normalised exactly like `resolveRole()`.

| Level | Who | Can |
|---|---|---|
| manage | Admin, owner, Accountant, Finance Officer, "Senior Finance Officer"… | everything below + refunds, clear/bounce cheques, payment settings (admin only) |
| take | Receptionist / Front Desk, **Cashier, Billing Officer** | record payments, send STK / card requests, cancel a pending online request |
| member | everyone else in the hospital | view the ledger |

Cashiers can take money but cannot refund it (segregation of duties). Staff whose `staff.status` is
Suspended, Terminated, Rejected, Pending Approval or Inactive drop to *member*.

## Rules worth knowing

- **Overpayment is impossible.** Pending STK pushes and uncleared cheques reserve their amount.
  Only a *completed* refund re-opens the balance.
- **Transaction references** (M-Pesa codes, bank refs, cheque numbers):
  - never twice on the same invoice;
  - a code confirmed by a gateway can't be typed in again elsewhere;
  - a typed M-Pesa/Airtel code may cover several invoices **of the same patient** (consultation +
    pharmacy) but not another patient's;
  - one bank transfer or cheque may cover several patients (corporate payers).

  Re-use is always **flagged for review**. It shows in Cash-up → "Needs attention".
- **Legacy screens** (lab, pharmacy, consultation, wards, Credit, Insurance, SHA claims…) still write
  `invoices.paid_kes`. An **increase** becomes a ledger row tagged `legacy_sync`. A **decrease** is refused:
  the ledger value is kept and the attempt is logged as `legacy_paid_decrease_blocked` in the audit log.
  Real reversals are refunds by finance.
- Invoices with payments can't be deleted. Cancel them and refund instead.
- STK rows on the M-Pesa screen are read-only (marked *auto*). Their status comes from the gateway.

## Not covered

- No live gateway has been called; adapters follow provider docs and are tested with mocked HTTP.
- Gateway refunds: Paystack and Flutterwave only. Daraja (B2C), Pesapal, cash and bank refunds are paid out
  manually, then recorded in the app.
- Pharmacy POS (`sales_ledger`), eTIMS fiscal receipts and SHA/insurer remittance matching are separate.
